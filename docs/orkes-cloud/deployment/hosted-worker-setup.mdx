# Hosted worker setup guide on Azure

Hosted Workers run your Conductor cluster's system task workers in your own cloud subscription, while the cluster's server, database, and cache stay Orkes-hosted. Only the worker compute moves into your subscription, connecting back to your existing Orkes-hosted cluster.

**Note**: Hosted Workers is currently supported only for Customer-hosted Azure clusters.

## Prerequisites

Ensure the following are set up in your Azure subscription.

#### Resource providers

Activate the following resource providers in your subscription:

```
Microsoft.ContainerService
Microsoft.Network
Microsoft.Compute
Microsoft.ManagedIdentity
Microsoft.Authorization
Microsoft.Resources
```

#### Resource group

Create a resource group in a region of your preference. Supported regions are:

- East US (eastus)
- East US 2 (eastus2)
- Central US (centralus)
- South Central US (southcentralus)
- West US 3 (westus3)
- Australia East (australiaeast)
- France Central (francecentral)
- North Europe (northeurope)
- West Europe (westeurope)
- Qatar Central (qatarcentral)
- UK South (uksouth)
- Canada Central (canadacentral)
- Canada East (canadaeast)
- Germany West Central (germanywestcentral)
- UAE North (uaenorth)

**Tip:** For lowest latency, we recommend choosing the same region as your Conductor cluster, unless you have data residency or other requirements that mandate otherwise.

#### Azure CLI

[Install the Azure CLI](https://learn.microsoft.com/en-us/cli/azure/install-azure-cli?view=azure-cli-latest) on a local machine, and log in to the same Azure subscription you'll use for this deployment. You'll use it to run the verification command in this guide, and later to run the authorization script for deployment.

#### Quotas and VM availability

Ensure your subscription has sufficient quota in the region you selected:

| Resource | Minimum quota |
| --- | --- |
| Standard DADSv5 Family vCPUs | 4 |
| Total regional vCPUs | 4 |

Confirm the VM type required for the deployment is active in your subscription. Log in to the Azure CLI with the same subscription you'll use for the hosted worker, and replace `<region>` with your resource group's region:

```shell
az vm list-skus -l <region> -o table | grep "NotAvailableForSubscription" | grep "Standard_D2ads_v5"
```

A blank result is expected. If it instead reports non-availability of this VM type in the specified region, reach out to Azure to activate it in your subscription before deployment.

#### VNet and IP range

VNet creation is optional. Choose whichever fits your address management. You'll enter the corresponding value later in this guide, during provisioning:

- If you are using an existing subnet: supply its resource ID. Recommended option.
- If you are using an existing VNet: provide its name and an available range within it.

Supported IP ranges are `/25` through `/28`.

#### Outbound network access

If your policy requires egress through a firewall or proxy (`outboundType: userDefinedRouting`), let Orkes know before you begin provisioning.

## Steps to provision the hosted worker

In this section, you'll log in to the Orkes Cloud Portal to start deployment of the hosted worker.

Your email must be shared with Orkes before you can create a cluster. If the **Create New Cluster** option isn't available to you in the portal, contact your Orkes representative to be added.

1. Log in to the [Orkes Cloud Portal](https://cloud.orkes.io/).
2. Go to **Clusters** from the left navigation menu.
3. Select **Create New Cluster** > **Create New Customer Cluster**.
4. Select **Azure** as the cloud provider.
5. Select the **Deployment Type** as **Worker hosting (attach workers to an existing cluster)**.
6. Configure the following parameters:
   1. **Attach To Cluster:** Select the Conductor cluster these workers will attach to.
   2. **Worker Environment Name**: Max 18 characters; letters, numbers, and hyphens are allowed (can't start with a hyphen). If left blank, this defaults to the parent cluster's name plus `-wk`.
   3. **Azure Resource Group Name**: The name of the Azure resource group you created earlier.
   4. **Azure Region**: Select the region where this hosted worker needs to be deployed.
7. Select **Generate Script**.

This creates a script that the administrator of your Azure account must run using the Azure CLI. The script creates the applications, service principals, roles, and role assignments required for the provisioning, and prints the service principal credentials you'll enter next to continue.

#### To run the script:

1. On the local machine where you'll run the script, log in to Azure and target the correct subscription. Replace `${AZURE_SUBSCRIPTION_ID}` with your subscription ID:

   ```
   az upgrade
   az bicep upgrade
   az login
   az account set -s "${AZURE_SUBSCRIPTION_ID}"
   ```

2. Run the downloaded script:

   ```
   sh <downloaded script>
   ```

If any part of the script fails partway through, note the values already displayed, then rerun the script after resolving the issue; only the failed parts run again. The Service Principal Password is displayed only once, so be sure to save it: rerunning the script after the service principal already exists will not print it again.

#### To verify authorization:

1. From the script output, enter the following values into the Orkes Cloud portal:
   - **Azure Subscription Id**
   - **Azure Service Principal Application Id**
   - **Azure Service Principal Password**
   - **Azure Tenant Id**
2. Select **Verify Authorization & Continue**.

#### To complete provisioning:

1. Once verification succeeds, enter the following on the next screen:
   - **VNet name**
   - **CIDR range of the VNet** (Enter a block-aligned CIDR from /25 to /28, e.g. `10.0.1.0/26`. Choose a range that does not overlap your existing networks.)
   - **Existing Subnet ID** (Optional; use this instead of the VNet fields above if you'd rather attach to a subnet you've already created; supplying it skips VNet creation)
   - **Environment Type**: Tag the worker environment (Production, Staging, Development, Test, or Proof of Concept).
2. Select **Create Provisioning Workflow**.

You can track provisioning status from the cluster listing page.

## Next Steps

Once your cluster is up and running, see [Managing Your Cluster](/content/orkes-cloud/managing-your-cluster) to see what you can do with it from the portal. Note that only a subset of tabs and actions apply to a hosted worker environment.
