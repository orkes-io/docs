# AWS Lambda Integration with Orkes Conductor

:::info Available since
- v5.3.0 and later
:::

Integrating AWS Lambda with Orkes Conductor lets you build workflows that interact with your AWS Lambda using the following operations:

- List Functions
- Create Function
- Get Function Details
- Update Function Configuration
- Invoke Function
- Delete Function

This guide explains how to set up and use the integration. Here's an overview:

1. Get the required credentials from AWS.
2. Configure a new AWS Lambda integration in Orkes Conductor.
3. Use AWS Lambda integration in workflows.

## Step 1: Configure AWS authentication and permissions

Choose how Conductor authenticates to AWS. Credentials belong to the saved integration, not to individual workflow tasks.

| Authentication | When to use it | Required configuration |
| -------------- | -------------- | ---------------------- |
| **Access Key** (`ACCESS_KEY`) | Use an IAM user's access keys or temporary AWS credentials. | Access Key ID and Secret Access Key. Include the Session Token when using temporary credentials. |
| **Conductor Role (worker identity)** (`CONDUCTOR_ROLE`) | Use the AWS identity available to the worker running the operation. | Configure the worker's AWS identity, such as an EC2 instance profile or ECS task role. |
| **Assume Role (from worker identity)** (`ASSUME_ROLE`) | Have the worker assume a target IAM role using AWS STS. | Target Role ARN and a nonblank External ID. The worker identity needs `sts:AssumeRole` on that role, and the target role must trust the worker identity. |

### Access keys

1. In the [AWS Console](https://console.aws.amazon.com), open **IAM** > **Users** and select or create a user.
2. Attach permissions for the operations you intend to use, as described below.
3. Open **Security credentials** > **Access keys** > **Create access key**.
4. Follow the creation flow and copy the access key ID and secret access key.
5. If you use temporary credentials instead, obtain all three values: access key ID, secret access key, and session token.

Saved temporary access keys and session tokens are not automatically refreshed. Update the integration before they expire, or use a worker identity or assumed role whose credentials can be refreshed by the AWS SDK.

### Worker identity and assumed roles

**Conductor Role** uses the worker's AWS credential provider chain. Configure that identity on the worker deployment; the identity used to log in to the Conductor UI is separate.

For **Assume Role**, the worker's source identity needs permission to assume the target role. The target role's trust policy must allow that source identity and the configured external ID. For example:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::123456789012:role/conductor-worker"
      },
      "Action": "sts:AssumeRole",
      "Condition": {
        "StringEquals": {
          "sts:ExternalId": "YOUR_EXTERNAL_ID"
        }
      }
    }
  ]
}
```

Replace the example principal and external ID with your deployment's values. The target role carries the Lambda permissions described below. See [AWS guidance on external IDs](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_create_for-user_externalid.html).

:::note
Select the authentication mode explicitly. Leaving access-key fields empty in **Access Key** mode does not switch to the worker identity. Choose **Conductor Role (worker identity)** for that behavior.
:::

### Permissions for the integration identity

The integration identity is the IAM user, worker role, or assumed target role selected above. Grant it the operations you intend to execute. This example covers all supported Lambda operations:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ListFunctions",
      "Effect": "Allow",
      "Action": "lambda:ListFunctions",
      "Resource": "*"
    },
    {
      "Sid": "ManageFunctions",
      "Effect": "Allow",
      "Action": [
        "lambda:GetFunction",
        "lambda:CreateFunction",
        "lambda:InvokeFunction",
        "lambda:UpdateFunctionConfiguration",
        "lambda:DeleteFunction"
      ],
      "Resource": "arn:aws:lambda:us-east-1:123456789012:function:connected-apps-*"
    },
    {
      "Sid": "PassLambdaExecutionRole",
      "Effect": "Allow",
      "Action": "iam:PassRole",
      "Resource": "arn:aws:iam::123456789012:role/lambda-execution-role",
      "Condition": {
        "StringEquals": {
          "iam:PassedToService": "lambda.amazonaws.com"
        }
      }
    }
  ]
}
```

Replace the region, account ID, function-name pattern, and execution-role ARN. `ListFunctions` requires `Resource: "*"`; other actions can be limited to your functions. See the [Lambda permissions reference](https://docs.aws.amazon.com/service-authorization/latest/reference/list_lambda.html).

### Execution role for Create Function

The **Role** input to **Create Function** is a separate role that the new Lambda function assumes when it runs. It must trust `lambda.amazonaws.com` and have permissions needed by the function code. For a basic echo function, attach the AWS managed policy **AWSLambdaBasicExecutionRole** to enable CloudWatch logging.

The integration identity needs `iam:PassRole` on the exact execution-role ARN, including any IAM role path. In **Assume Role** mode, add this permission to the target role Conductor assumes. See [Lambda execution roles](https://docs.aws.amazon.com/lambda/latest/dg/lambda-intro-execution-role.html) and [PassRole permissions](https://aws.amazon.com/blogs/security/how-to-use-the-passrole-permission-with-iam-roles/).

## Step 2: Add an integration for AWS Lambda

After obtaining the credentials, add an AWS Lambda integration to your Conductor cluster.

**To create an integration:**

<ol>
<li>Go to <strong>Integrations</strong> &gt; <strong>Connected Apps</strong> from the left navigation menu on your Conductor cluster.</li>
<li>Select <strong>+ New integration</strong>.</li>
<li>In the <strong>Cloud</strong> section, choose <strong>AWS Lambda</strong>.</li>
<li>Select <strong>+ Add</strong> and enter the following parameters:</li>
</ol>

| Parameter | Description | Required/Optional |
| --------- | ----------- | ----------------- |
| Integration name | A name for the integration. | Required. |
| Authentication | **Access Key**, **Conductor Role (worker identity)**, or **Assume Role (from worker identity)**. Defaults to Access Key. | Required. |
| Access Key ID | AWS access key ID. Shown for Access Key authentication. | Required for Access Key. |
| Secret Access Key | Matching AWS secret access key, stored as a secret. | Required for Access Key. |
| Session Token | AWS session token, stored as a secret. Supply it when the access key is temporary. | Required for temporary access keys; otherwise optional. |
| Role ARN | Target IAM role assumed using the worker identity. Shown for Assume Role authentication. | Required for Assume Role. |
| External ID | External ID required by the target role's trust policy, stored as a secret. | Required for Assume Role. |
| Region | AWS region used for Lambda and STS. Defaults to `us-east-1`. | Required. |
| Description | A description of the integration. | Required. |

<ol start="5">
<li>(Optional) Toggle the <strong>Active</strong> button off if you don't want to activate the integration instantly.</li>
<li>Select <strong>Save</strong>.</li>
</ol>

## Step 3: Use AWS Lambda integration in workflows

Once the integration is ready, this can be used directly within the workflows.

**To use AWS Lambda integration in a workflow:**

<ol>
<li>Go to <strong>Definitions</strong> &gt; <strong>Workflow</strong> from the left navigation menu on your Conductor cluster.</li>
<li>Select <strong>+ Define workflow</strong>.</li>
<li>In your workflow, select the (<strong>+</strong>) icon and select <strong>Connected Apps</strong>.</li>
<li>In <strong>Add Task</strong> panel on the right, search for <strong>AWS Lambda</strong>, and select the integration created in <a href="/content/integrations/aws-lambda#step-2-add-an-integration-for-aws-lambda">Step 2</a>.</li>
</ol>

The following operations are available for use with this integration.

| Operation | Description |
| --------- | ----------- |
| [List Functions](/content/integrations/aws-lambda-operations#list-functions) | Lists Lambda functions in the configured AWS region. |
| [Create Function](/content/integrations/aws-lambda-operations#create-function) | Creates a new Lambda function from a base64-encoded ZIP package. |
| [Get Function Details](/content/integrations/aws-lambda-operations#get-function-details) | Retrieves full configuration details of a specific Lambda function, including runtime, handler, IAM role, memory, timeout, and code location. |
| [Update Function Configuration](/content/integrations/aws-lambda-operations#update-function-configuration) | Updates the configuration of an existing Lambda function, without redeploying code. |
| [Invoke Function](/content/integrations/aws-lambda-operations#invoke-function) | Invokes a Lambda function with a JSON payload. Supports synchronous (`RequestResponse`), asynchronous (`Event`), and validation-only (`DryRun`) invocation types. |
| [Delete Function](/content/integrations/aws-lambda-operations#delete-function) | Permanently deletes a Lambda function from your AWS account. |

<ol start="5">
<li>Select the required operation, configure the parameters, and select <strong>Save</strong> &gt; <strong>Confirm</strong>.</li>
<li>Select <strong>Execute</strong> to run the workflow.</li>
</ol>

For the complete operations parameters and output reference, see [AWS Lambda Operations Reference](/content/integrations/aws-lambda-operations).

## Troubleshooting

- **AccessDenied for iam:PassRole:** Add the permission to the integration identity, including the target role in Assume Role mode. Its Resource must match the exact execution-role ARN in Create Function.
- **Assume Role fails:** Check the worker identity's `sts:AssumeRole` permission, the target trust policy, and the External ID configured in the integration.
- **Expired temporary credentials:** Update the access key, secret key, and session token together. Saved temporary credentials are not refreshed automatically.
- **HTTP 200 but task failed:** For synchronous invocation, inspect `functionError`, `error`, and `response`; Lambda can report a function error in an HTTP 200 response.
